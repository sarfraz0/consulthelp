## Findings

| ID | Priority | Finding | Implementation |
|---|---|---|---|
| SS-01 | P1 for the declared fixed-budget contract | Losing a checkpoint for a partial transfer silently starts a fresh budget and permits more pushes | `Read-TransferState`, lines 1205–1217; `Invoke-TransferPush`, lines 1400–1420 |

### SS-01 — Missing checkpoint resets a previously expired transfer

The checkpoint is the only persisted start-time anchor. If it is absent, `Read-TransferState` returns a new state with the current invocation’s `StartedUtc`, regardless of existing transfer history. `Invoke-TransferPush` subsequently reconciles that fresh state with real local/remote commits and permits work under the new hour.

**Reproduction with actual implementation functions and local Git:**

1. Created a two-shard plan, with canonical plan creation/start timestamps aged to a prior transfer window.
2. Created the first exact transfer commit through `New-ItemCommit`, pushed it to the local bare remote, and persisted a matching one-item checkpoint whose start was two hours earlier.
3. Repeating Push with that checkpoint present was correctly rejected with `Deadline`.
4. Moved only that checkpoint aside to simulate loss; the plan, source and Git history remained unchanged.
5. A fresh invocation of the same Push accepted the missing checkpoint, saved a new start, reconciled the first commit and pushed the second shard to completion.

The timestamps were deliberately aged fixture data; the test did not wait two hours. The observed result is actual additional local-remote publication after loss of an expired state record, not merely construction of an in-memory date. Source bytes were not corrupted and the test did not demonstrate an arbitrary unrelated-file upload.

**Impact:** normal checkpoint custody is essential, but an accidentally missing/deleted/restored state file must not silently turn the same partial transfer into a new budget. The documented original-hour contract does not hold across this recoverable evidence of prior work. The test preserved pacing through reconciliation; it does not establish a pacing bypass.

**Correction:** distinguish first use from missing prior state using actual transfer history and a durable start anchor. At minimum, refuse a missing checkpoint when exact prior transfer commits are already present rather than manufacturing a fresh start. Specify recovery when the original anchor cannot be established. Verify genuine first Push, interrupted local/unverified push, lost/corrupt checkpoint, expired resume and completed re-verification independently. Do not infer a fresh budget from an edited plan or automatically reset history.

### SS-02 — Exited-parent cleanup abandons a live owned descendant

`Wait-NativeExit` waits both for Git exit and for its redirected stdout/stderr streams to finish. A helper inheriting those streams can keep them open after Git exits. On timeout, `Invoke-TransferGit` calls `Stop-OwnedProcess`, but that function immediately returns when the parent process `HasExited` is true. It never invokes the tree-cleanup adapter for that path.

**Reproduction:** a synthetic installed executable spawned an owned sleeping helper that inherited the pipes, recorded its PID and exited. The real native adapter reached `GitTimeout` near a finite remaining deadline. The helper remained alive after the adapter returned; an instrumented taskkill adapter was never invoked. Test cleanup then terminated only the recorded fixture-owned helper. No network or ongoing real Git transfer was involved.

**Platform limit:** the actual reproduction uses Linux processes and a synthetic executable to exercise unchanged production functions. It proves the exited-parent control-flow/ownership gap; it does **not** certify Windows process-tree APIs or demonstrate a Windows credential-helper incident. The same unconditional `HasExited` return makes this a target release concern that needs a Windows reproducer.

**Correction:** establish owned descendant lifetime independently of a surviving parent PID, using supported Windows process ownership/containment with policy review. Treat cleanup failure as a retained-process outcome, and test parent exit, inherited pipes, grandchildren, helper cancellation, timeout and hard termination. Do not kill by image name or target unrelated processes.

The sender accepts a 256 MiB encoded-file cap, while hosting may cap blobs much lower; for example, repository providers can reject files below the sender’s configured maximum. Choose volume sizes from the actual host policy. Default 10 MiB binary Embelish volumes encode to roughly 13.3 MiB, before any host-specific restrictions.

Plans/checkpoints retain private paths and hashes. Logs use an allowlist, unlike the [current Embelish logging gap](../embelish/audit-2026-10-20.md#eb-06--raw-diagnostic-data). Dedicated secret/duplicate-code scanner tools were unavailable; no clean scanner or full automated coverage claim is made.

## Engineering measurements and release order

The per-function AST guideline count finds `Read-TransferJson` complexity 12/nesting 4, `Test-JsonElement` complexity 11, and `Assert-ControlledDirectory` nesting 4. Nesting counts if/loop/switch/try containers; complexity counts the guidelines’ if/elseif, loops, non-default switch clauses, catches and Boolean `-and`/`-or`. Noncomment token-bearing body lines exclude declarations/parameters. These measurements are maintainability evidence, not native correctness tests; review/document focused exceptions or refactor only with preserved behavior. Entry metrics are recorded separately in the verification note.

1. Correct SS-01/SS-02 with failure/restart tests; retain all 68 passing regressions and the exact source/index/commit/remote checks.
2. Resolve Embelish’s destructive publication and restore defects before using this pair as a complete backup/transfer/restore workflow.
3. Execute the supported Windows runtime/filesystem/credential/process matrix. Keep hooks, signing, TLS, endpoint controls and standard-user execution intact.
4. Approve release only after persisted recovery, the original deadline and the recipient’s complete restore outcome are demonstrated on the target. This audit is a release hold, not a claim that production execution passed.
