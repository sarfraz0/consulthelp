### F1 — Initial planning budget selects an integer `Math.Min` overload

`New-TransferContext` stores an integer `GitTimeoutSeconds` and a null `DeadlineUtc`. `Get-RemainingTime` returns positive infinity for that initial planning context. The next expression is:

```powershell
$limit = [math]::Min($Context.GitTimeoutSeconds, $remaining)
```

The reproduced invocation selects the integer overload and tries to convert infinity to `Int32`, throwing before starting the first Git command. The minimal expression `[math]::Min([int]60, [double]::PositiveInfinity)` reproduces the failure, as does the actual native adapter with the initial context shape.

**Impact:** normal Plan cannot reach even its Git-version/repository checks in the reproduced path. Push initializes a finite deadline before its repository checks, so this finding specifically exposes the initial planning path.

**Remediation:** make the intended floating-point overload explicit and test both null/infinite and finite remaining budgets with integer CLI timeouts. Check fractional budgets as well as expiration. Verify the correction on Windows PowerShell 5.1.

### F2 — Atomic replacement receives an empty backup path

The first write to a new JSON filename succeeds. A second write to that same path reaches:

```powershell
[System.IO.File]::Replace($temporary, $Path, $null)
```

The reproduced call passes an empty string for the string-typed backup argument, and `File.Replace` throws an argument exception. A create-then-replace test fails with the actual writer. Initial state publication followed by `Sync-TransferState` also reaches this failure before normal transfer work proceeds. A lower-level send test reaches remote verification and then fails to checkpoint its success for the same reason.

**Impact:** checkpoint updates, reconciliation and resume cannot be considered reliable. A successful remote change can precede a later checkpoint failure; operators must inspect actual Git/remote state rather than infer that nothing was sent.

**Remediation:** pass a true null string to the documented API or use a deliberately managed valid backup path, preserving same-filesystem atomic replacement and previous-good-state protection. A scratch-only `[NullString]::Value` prototype passed replacement and allowed a one-shard local transfer to complete. That prototype was not applied to the repository implementation or certified on Windows.

### F3 — Duplicate detection compares XML reader names before JSON-name normalization

The actual reader rejects `{"Name":1,"Name":2}` but accepts:

```json
{"Name":1,"\u004eame":2}
```

The final object contains `Name = 2`. `Test-JsonElement` compares the XML reader's `LocalName`, while `ConvertFrom-Json` subsequently decodes the escaped JSON property name. The two stages therefore disagree about whether the property names are duplicates.

**Impact:** ambiguous documents pass a policy that explicitly promises duplicate-key rejection. The later schema and source/Git guards still run, but they see the final decoded values rather than every original occurrence.

**Remediation:** canonicalize actual JSON property names before duplicate detection, or explicitly reject escaped field-name spellings in this restricted schema. Keep parsing compatible with 5.1 and test ordinary, escaped and case-colliding duplicates at nested schema levels.

### F4 — Missing string-type checks turn comparisons into collection filters

The complete manifest verifier accepts a manifest whose shard entry has `Hash: []`, despite there being no actual matching hash string. Separate tests also accept `Name: []` and `Archive: []`. Wrong scalar hash strings are correctly rejected.

PowerShell comparison operators return filtered collections when the left operand is a collection. For an empty array, expressions such as `$Entry.Hash -cne $Record.Sha256` produce an empty result, which evaluates false inside the rejection condition. Counting object properties does not validate their types.

**Impact:** verification against the optional source checksum manifest can be bypassed with malformed field types. The frozen plan's independently computed SHA-256 and Git blob checks remain separate safeguards.

**Remediation:** validate string types and formats for `Archive`, `Name` and `Hash` before comparing values. Review other state/manifest identity comparisons for the same collection semantics. Add malformed-type cases for null, arrays, objects and numbers, alongside valid and mismatching scalar values.

### F5 — Index validation is inside a loop that can be skipped

`Invoke-TransferPush` reconciles state and then validates the index only inside `while ($verified -lt $pending.Count)`. With zero pending items, the loop is skipped and the operation reports completion despite a foreign staged file.

**Evidence:** a fixture with a shard already in the base commit, a zero-pending plan and a subsequently staged unrelated file was accepted. This test used the scratch writer prototype from F2 so that checkpoint failure did not mask the later control-flow gap.

**Impact:** the broad documented promise that foreign staged changes stop Push is not enforced on the no-work path. The reproduced case sends no extra data and leaves the unrelated staged file in place.

**Remediation:** validate the index before reporting completion, including zero-item and completed-resume paths. If allowing a foreign index during read-only completed verification is intentional, narrow the documented contract explicitly and test that policy instead.

### F6 — JSON timestamp behavior changes after Windows PowerShell 5.1

The actual writer emits ISO UTC timestamp strings. On PowerShell 7.6.6, the actual JSON reader materializes them as `DateTime`. `Assert-TransferPlan` requires string-valued `CreatedUtc`, and `ConvertFrom-UtcStamp` rejects a `DateTime`. Plan input loading fails with `PlanString`; checkpoint reloading fails with `UtcTimestamp`.

Microsoft documents the timestamp conversion change beginning in PowerShell 6. This finding is **not evidence that ISO strings fail the same way on Windows PowerShell 5.1**. The runtime guard currently checks Windows and FullLanguage rather than explicitly constraining execution to Windows PowerShell Desktop.

**Remediation:** preserve and validate timestamp semantics across the runtimes intentionally supported, or make the runtime contract explicit and enforce it. A PowerShell-7-only JSON switch cannot become an unconditional requirement in a 5.1 script. Test writer/reader round trips before counting mocked or in-memory resume checks as persistence coverage.

### Isolation and prototype boundaries

- The complete executable was not dot-sourced and its production host guard was not changed. Actual function definitions were loaded using the AST; the real Windows entry point remains unexecuted.
- Synthetic Git repositories and filesystem-only bare destinations were created outside the working repository. `GIT_ALLOW_PROTOCOL=file` restricted Git transport. No real user shards, corporate credentials or remote transfer destination were used.
- Downstream test contexts supplied a finite deadline to isolate F1 while retaining an integer timeout. This is a test context, not evidence that default Plan works.
- Two passing scenarios explicitly used a scratch-only writer correction: atomic replacement and a one-shard transfer with remote blob verification. F5 was also reproduced with that writer correction. These results are separated from claims about the unmodified writer.
- A controlled quiet child exercised the actual native timeout-detection loop. The fixture cleaned up only its owned child; Windows `taskkill /T /F` behavior was not simulated or certified.
- Temporary test scripts, captures and fixtures are development artifacts outside the repository. No production bypass, testing framework or additional implementation dependency was added.

### Useful guards that passed in isolation

The pass cases cover literal spaces/brackets and a Unicode shard name; local-only planning with an unreachable destination; multiple sets and manifest-after-shards ordering; empty/gapped/noncanonical shards; 256 MiB source and 8 MiB JSON rejection; deep JSON refusal; ordinary duplicate rejection; preservation on NewOnly refusal; changed sources/branches/destinations; multiple push URLs, mirror mode and credential-bearing URLs; foreign staged planning changes and foreign commit history; byte-changing clean-filter rejection; a rejecting commit hook; exact single-file commit/blob checks; interrupted-push reconciliation from local bare-remote evidence; remote rewind and excess local-history refusal; repository-handle overlap; plan-path/link ancestry guards; elapsed/future/deadline and 3000-second wait-boundary checks; the 2 MiB stream limit; timeout detection; and diagnostic-field allowlisting with synthetic secrets.

The standalone smoke checks used a relocated script with no referenced `docs/` or XML. Native `-?` returned generated syntax, and an ordinary Plan invocation reached its expected Windows-prerequisite refusal. Optional-help independence is preserved; these checks do not establish successful Windows transfer execution.

## Recommended correction order

1. Correct F1 and F2, then demonstrate standalone Plan → persisted input → Push → persisted resume on Windows PowerShell 5.1.
2. Tighten JSON and manifest type validation for F3/F4 and add adversarial schema regressions.
3. Enforce or explicitly refine the no-work index policy in F5.
4. Decide and test the intended PowerShell 6/7 support in F6 without adding a new runtime dependency.
5. Run Windows interruption, cleanup, signing/credential and scheduler acceptance before recording a target pass. Address and classify analyzer/metric findings after the behavior blockers have executable coverage.
