## Decision and scope

**HOLD general production release.** Existing-output preservation and restore isolation need correction before this script is used as a dependable backup/restore tool. Some unsafe behavior was already documented; this audit reproduces it and identifies additional cases. A passing archive round trip or clean analyzer result does not close the failures below.

Audited implementation: `embelish/embelish.ps1` **1.1.1**, commit `07482b581858145fd981b229a37373ee9927206c`, SHA-256 `3ecdebdbc6255c7b2166e3c885aaac475db6950a9beedcd715848fe463b10ecd`. This audit changes documentation only. No production implementation or runtime dependency was added.

Execution environment: Debian Linux, PowerShell 7.6.6/.NET 10.0.12, 7-Zip 25.01 x64 and PSScriptAnalyzer 1.24.0. Actual Windows PowerShell 5.1 and Windows 7-Zip execution are **NOT RUN**. All data, errors, passwords and destinations used here were synthetic; no real user archive, corporate data or publication was used.

### EB-01 — Previous generation and source-data deletion

`-Force` permits an existing destination and deletes matching old shards **before** native archive creation. A real in-file operation with a synthetic native executable returning exit 2 removed the old `bundle.7z.001.txt`, then failed. No new archive replaced it. This confirms the already documented delete-before-create limitation; `Force` is not transactional replacement.

There is also no source/output overlap guard. With source and destination set to the same synthetic directory, a matching shard that was part of the selected source was deleted before the failed native invocation. The remaining ordinary source file was untouched, but that selected input file was lost. The defect is stronger than merely losing a previous output generation.

**Correction:** reject unsafe overlap using canonical filesystem identities; build and validate a new generation separately; publish it without first deleting the last good generation. Retain prior data and disclose recovery artifacts on every failure. Verify aliases/junctions/hard links where supported, without assuming that textual prefix tests establish identity.

### EB-02 — Destructive and concurrent restore

The script always passes `-aoa` to 7-Zip and extracts straight into the requested destination. It neither locks that destination against another operation nor stages/restores a validated complete tree before publication.

Two actual 7-Zip reproductions:

1. An otherwise valid four-volume encrypted archive had one data byte corrupted, leaving the encrypted header readable. Restoring with `-Force` into a synthetic existing tree overwrote the previous `random.bin`. 7-Zip then reported an encrypted-file CRC failure, and the script exited 3. The prior file was not restored; a 3,146,049-byte output remained.
2. A restore began without `-Force` into an empty destination. While 7-Zip awaited the password, a synthetic concurrent writer created the matching destination file. Extraction silently overwrote it and the script reported success. The initial empty-directory check did not enforce no-overwrite at mutation time.

**Correction:** extract/test in an owned staging tree; reject source/output aliasing; acquire exclusive output ownership; preserve the previous tree when validation fails. Enforce the selected overwrite policy at publication, including late collisions. Filesystem publication and recovery need interruption/fault-injection tests on the target platform.

### EB-03 — Incomplete and ambiguous shard sets

The resolver checks only that the first numeric index is 1. Both `{001,003}` and `{001,0001}` were accepted. The latter gives two filenames the same logical volume number; the native extractor opens the constructed `.001` path and may ignore other accepted names. Missing middle volumes therefore reach native work and may leave partial extraction, while noncanonical/extra files undermine the reported set/count.

**Correction:** require unique canonical numbers, contiguous from 001, before any output mutation. Validate every expected name and reject ambiguous files. Trailing-volume completeness still requires trustworthy producer metadata or a complete native archive test; contiguous names alone cannot prove it.

### EB-04 — Explicit file selection does not work as advertised

Passing `one.7z.001.txt` in a folder containing `one` and `two` sets still scans both and throws the same multiple-set error. The error itself recommends selecting a `.001.txt` file, which cannot resolve that condition. Conversely, passing an existing `unrelated.json` in a folder with one shard set selects that other set rather than rejecting the non-shard input.

This matters to integration: Sendshards supports several archive sets in one source folder, but the receiver cannot restore each by selecting its file without first rearranging the downloaded sets.

**Correction:** validate a file argument against the shard naming contract and use its exact base to select one set. Preserve a clear refusal for ambiguous directory arguments. Test case sensitivity and Unicode on the target filesystem.

### EB-05 — Successful result with no archive output

A real CLI run used the valid parameter `-ArchiveBaseName .hidden`. On Linux, 7-Zip successfully created four encrypted volumes named `.hidden.7z.001` through `.004`. `Get-ChildItem` omitted them because enumeration lacks `-Force`. The script deleted staging in `finally`, returned `Succeeded=True`, `Status=Success`, `ShardCount=0` and exited 0. The destination contained no shards.

**Platform limit:** this is a Linux/Core reproduction. Leading dots alone do not give files the Windows Hidden attribute; this does not establish the same trigger on Windows. It does expose the absence of an output-count/postcondition check and contradicts the advertised cross-platform behavior.

**Correction:** enumerate the owned generated volumes reliably, validate a nonempty contiguous output and byte counts before publication, and fail rather than reporting zero-output success. Keep the runtime support statement aligned with tested behavior.

### EB-06 — Raw diagnostic data

The logger accepts arbitrary supplied fields. A direct synthetic marker was persisted, and an actual CLI missing-source failure recorded the synthetic source name/path inside `run.error.message`. The password was not exposed in these tests. This confirms the existing documented log-privacy limitation rather than a newly demonstrated password leak.

**Correction:** use an allowlisted diagnostic schema and stable error identifiers; keep paths/raw exception text out of shareable records. Test generated errors with synthetic path, username and payload markers. Retention and output logs must remain separate from business data and respect configured ownership.

## Additional production gaps

- **Memory and size contract:** base64 conversion reads complete volumes and encoded strings into memory. `VolumeSizeMegabytes` permits up to 1 TiB, without a corresponding memory/disk bound. Sendshards caps each encoded file at 256 MiB; encoded volumes larger than 192 MiB already exceed that bound. Git hosting may impose lower limits. Only the default/small-volume path has current native evidence.
- **Completeness and identity:** the producer emits no expected-volume/source inventory or checksum manifest. 7-Zip integrity checks and successful Git blob verification are not proof that the intended complete source tree was captured or that an archive has a trusted origin. Quiesce the source and define the required restore/inventory check.
- **Warnings:** native exit 1 maps to `CompletedWithWarning`, `Succeeded=True` and script exit 0. 7-Zip warnings can mean skipped files. A strict production backup must explicitly reject/review that result; it must not use process exit 0 alone as completeness evidence.
- **Password prompt documentation:** installed Linux 7-Zip 25.01 requested the creation password once in the observed invocation, rather than the earlier two-prompt documentation and existing verbose text. Native prompt count and Windows console behavior need validation; do not assume a confirmation prompt prevents a mistyped password.
- **Engineering review:** the guideline AST count covers all 15 functions and the entry block. `Invoke-EmbelishOperation` reaches the default 80 noncomment body lines (complexity 10, nesting 3); the measured functions and entry fit the stated defaults. Count token-bearing executable body lines, excluding declarations/parameters/comments; nesting counts if/loop/switch/try containers. These limited metrics do not establish business correctness. Dedicated duplicate-code and secret-scanner tools were unavailable and were not claimed to pass.

## Release gates

1. Fix EB-01/EB-02 and verify old-output preservation, source/output separation, late collisions, concurrent invocation, failed native work and interrupted publication.
2. Correct shard validation/selection and false-success postconditions; make log/privacy and warning/completeness policy explicit.
3. Run the corrected standalone CLI on the supported Windows PowerShell 5.1/7-Zip builds, with an actual interactive console, script installation under `scripts/`/an independent tools directory, spaces/brackets/Unicode and optional XML absent.
4. Exercise denied access, disk-full, large inputs, corrupt/missing/mixed shards, cancellation, abrupt termination, cleanup and restore into existing destinations. Confirm hashes and expected tree/inventory after restoration.
5. Validate approved signing/application-control/endpoint behavior on the managed target. No policy workaround or exclusion is part of this audit.

A restricted pilot with fresh, distinct versioned output and restore directories, one writer and retained originals reduces some risks; it is not a substitute for the failed release gates.
